\section{Reference system}
\label{sec:meth-machine}

All measurements in this work come from a single system that hosts all
three compared architectures: a general-purpose processor (CPU), a
discrete graphics unit (GPU), and a neural processing unit (NPU)
integrated into the same die as the processor. This isolates
differences between implementations from differences between platforms,
but introduces a constraint that shapes the measurement conditions: the
system is a laptop, so the three units share a common thermal and power
budget, handled as described in section~\ref{sec:meth-conditions}.

The processor has eight physical cores with simultaneous multithreading.
All measurements run with one thread per physical core, so no two threads
share a vector unit. The cache hierarchy sets the knee points of the
measured bandwidth scale (section~\ref{sec:meth-roofline}): depending on
input size and data type, the working set may fit in L2, L3, or only
main memory, and each implementation is compared against the ceiling for
its own working set.

Main memory is arranged as two identical \qty{16}{\gibi\byte} modules in
dual-channel mode at 5600 MT/s. A single-channel arrangement would halve
the available bandwidth, so a memory-bound implementation would give
substantially different results on an otherwise identical system.

The neural processing unit has no memory of its own. It is fed from the
same DDR5 through the same memory controllers as the processor, on the
same silicon die. This has two consequences that recur throughout
this work: the cost of preparing data on the host is not separable from
the cost of the computation itself, and the energy meter used covers the
whole package rather than the AIE tiles individually
(section~\ref{sec:meth-energy}).

The figures in table~\ref{tab:machine} were verified by the system itself
rather than taken from manufacturer datasheets.

\section{Structure of the measurement harness}
\label{sec:meth-harness}

The measurement harness has four layers, with one principle running
through the design: the measurement procedure is common to all
architectures, and only the compute kernel differs, so no implementation
controls how it is itself measured.

The first layer is a shared C++ core used by all three implementations.
It reads parameters, generates the input, schedules the bitonic
network's stages, reads the energy meters, runs the warm-up and
measurement loop, checks correctness, and prints the report. All of this
happens in one place, so the timing and energy measurements of every
architecture are defined by the same code.

The second layer consists of the per-architecture executables. Each
implements the same interface for the three compared algorithms, namely
bitonic sort, map-reduce with local heaps, and the reference implementation,
providing only the function that performs the computation. This function
is called by the shared measurement loop of the first layer.

The third layer is the sweep driver. It enumerates the parameter space of
section~\ref{sec:meth-parameters} and runs each case as a separate
process, recording its output verbatim along with its outcome, so that
each case starts from a clean memory state and the failure of one does
not invalidate the sweep.

The fourth layer converts the raw results into tables and plots, and
operates on the same report text the user reads. There is no separate
output path to the tools, so the values shown in the plots are by
construction the values printed by the executable. The execution
environment is stored alongside the results, as described in
section~\ref{sec:meth-conditions}, and the commands that produce each
stage are given in appendix~\ref{app:reproducibility}. The overall
structure is summarised in figure~\ref{fig:meth-harness}.

\section{Measured quantities}
\label{sec:meth-quantities}

\subsection{Measurement scopes: algo and end-to-end}
\label{sec:meth-energy-scope}

Comparing three architectures requires a decision about what counts as
cost. An accelerator that completes the computation very quickly but
requires the whole input to be transferred to and from main memory is not
necessarily faster than a processor working in place, so each case is
measured in two scopes rather than one.

The end-to-end scope covers the whole call from the host's point of
view: everything required so that, given an input in main memory, the
result is also found in main memory. The algo scope covers only the
region in which the computation itself executes. The difference between
the two is the cost imposed by heterogeneity itself, and is summarised
per architecture in table~\ref{tab:scopes} and schematically in
figure~\ref{fig:meth-scopes}.

        \hline

        NPU & region of the offload & device discovery, loading the offload configuration \\

    \end{tabular}
    \caption{The content of the two measurement scopes per architecture.}
    \label{tab:scopes}
\end{table}

\input{figures/meth-scopes}

For the processor the two scopes coincide by definition, since it is
itself the accelerator and there is no host cost to subtract. Any other
choice would give it an advantage it does not deserve.

The energy meter opens and closes at exactly the same points in the code
as the corresponding timer, so time and energy refer to the same region
of execution and are directly comparable. A third, wider window around
the entire measurement loop is additionally recorded as an upper-bound
sanity check, discussed in section~\ref{sec:meth-energy}.

The choice of scope therefore determines the question a measurement
answers: end-to-end is the fair scope for comparing across architectures,
since none of them hides its own data-transfer cost, while algo is
useful for comparing implementations within the same architecture, but
not sufficient on its own for claims across architectures, precisely
because it omits the transfers.

\subsection{Timing}
\label{sec:meth-timing}

The two scopes are not necessarily measured with the same mechanism. The
end-to-end scope is always measured with a host clock, on either side of
the call, since by definition it concerns time as perceived by the host.
The algo scope is measured with whatever mechanism each architecture
provides for the region of its own computation.

On the graphics unit the measurement cannot be done with a host clock.
Kernels launch asynchronously: the call returns as soon as the kernel is
placed in the command stream, not when it completes. A host clock
would therefore measure the time of the launch rather than of execution,
and forced synchronisation would add its own cost to the kernel. Events,
recorded within the command stream and timed by the device itself, are
used instead.

On the neural processing unit there is no equivalent device-side meter,
so the algo scope is defined by a host clock around the region of the
offload. This region does not contain only the execution on the tiles:
it includes allocating and preparing the buffers, dispatching the jobs,
and the final merge of the partial results on the host. This quantity
should therefore be read as the cost of the entire offload procedure, not
as the tiles' compute time. This distinction is essential for the conclusions
of chapter~\ref{ch:npu}.

Three quantities per scope are derived from the 50 measured repetitions
of each case: the mean, on which comparisons are based; the standard
deviation, an indication of measurement
stability under the pinned conditions of section~\ref{sec:meth-conditions};
and the minimum, a lower bound on the achievable time. The meters used
have nanosecond-scale resolution, against measured regions of a few tens
of microseconds to hundreds of milliseconds, so the cost of the timing
itself is negligible and is not subtracted.

\subsection{Energy measurement}
\label{sec:meth-energy}

Energy is measured by the executable itself rather than by an external
wrapper monitoring the process. An external tool measures the whole
process, whereas the measurement loop occupies only part of it, and that
part differs systematically by architecture. Such a tool would introduce
a systematic bias in favour of architectures with lower initialisation
cost. The meters are therefore read from within the process, at exactly
the same points in the code as the timers of section~\ref{sec:meth-timing}.

The sources differ by architecture, but the scope remains symmetric. For
all architectures the energy of the processor package is measured via the
RAPL counters, and for the graphics unit the power draw of the card is
added. The end-to-end scope therefore corresponds to the total cost of
solving the problem for all three, and the graphics unit does not hide
the cost it imposes on the host.

The reported energy is the sum, not the mean, of the 50 repetitions: the
RAPL counters quantise each individual reading but accumulate without
reset, so the sum remains accurate even when each individual difference
is on the order of the quantisation step. Reading the counters requires
elevated privileges. When these are unavailable, the executable states
the measurement as unavailable rather than reporting zero as data.

Of the RAPL fields, only the package one is used: the core subfield was
found unreliable on this processor, recording only \qty{6}{\watt} under
full eight-thread load while package power increases by about
\qty{53}{\watt}.

For the graphics unit, the total-energy counter exposed by NVML also
proved unsuitable: it advances in steps of about \qty{20}{\joule} every
few tens of milliseconds, so bracketing a millisecond-scale kernel
returns an arbitrary multiple of the step. Three identical runs gave
values differing by more than a factor of four, while the corresponding
time differed by \qty{0.2}{\percent}. Instead, a helper thread samples
the card's instantaneous power every \qty{2}{\milli\second} and
integrates it over time. The underlying power reading itself refreshes
less often than this sampling period, so a single algo window of a few
milliseconds relies on a reading that has not had time to refresh.
Summing over 50 repetitions smooths this inaccuracy out without
eliminating it, unlike the millisecond-refreshing RAPL counters.

Beyond the gross value, net energy is also reported: the gross value
minus the energy the system would consume at idle over the same
interval, with idle power measured before each sweep for the full set of
counters of each architecture. The net quantity is preferable especially
for the neural processing unit, where static consumption of the rest of
the system dominates, and for the graphics unit, where it cancels the
cost of the sampling mechanism itself.

What these measurements cannot show must be stated. The package meter
covers the entire system-on-chip die: host cores, NPU tiles, uncore, and
memory controller, all under one shared meter, so a run on the neural
processing unit is measured as the total energy of the system while it
works, including host-side data preparation. This is a fair, symmetric
comparison of the cost of solving the problem, but it cannot show that
the unit performs the computation itself while consuming less energy,
since its own consumption is never separated from the host's. Isolating
it would require external metering equipment.

\subsection{Data traffic measurement}
\label{sec:meth-traffic}

Beyond time and energy, each run records the bytes it moved and the
operations it performed. These are the coordinates that place the run on
the plot of section~\ref{sec:meth-roofline}, so an error here does not
merely add imprecision, it can imply an entirely
wrong conclusion about what limits the implementation.

For this reason traffic is not estimated from a model but accumulated by
the code itself at the points where it occurs: per kernel launch on the
graphics unit, per group of fused passes on the processor, and per data
batch on the neural processing unit. This distinction matters because the
obvious estimate, element count times type size, assumes each element
is read once. Truncated bitonic sort instead traverses the working set
repeatedly, by a factor that is not constant: roughly sevenfold for k
much smaller than n, rising considerably and by architecture for the
larger values of k, where truncation ceases to pay off. Using the naive
estimate would make every implementation appear to use only a small
fraction of the available bandwidth, wrongly suggesting none of them come
close to the memory ceiling.

The count is checked by independent verification where feasible. For
bitonic sort with k up to 4096, the processor and the graphics unit
execute the same stage schedule and compute their traffic in entirely
separate code, yet arrive at the same value down to the last byte. This is
strong evidence the traffic model is correct. For map-reduce the two
values differ, as expected: although both maintain a local heap per
thread, the processor runs only a few threads while the graphics unit
runs thousands, with a correspondingly larger working space and an
additional tree merge within each thread block, so the two implementations
genuinely move different volumes of data.

Not every quantity is equally observable, and each run states the
quality of its own numbers. For bitonic sort, both bytes and operation
count are exact, since the stage schedule is fully enumerable. For
map-reduce the bytes are exact, while the comparison count is a lower
bound, because the local heaps' reordering is data-dependent. For the
reference implementation both quantities are lower bounds, since the
libraries' internal passes are not observable from the calling code.

Operations are measured in compare-exchanges rather than in
floating-point operations: top-k selection performs no arithmetic, so a
FLOP-based quantity would not correspond to anything actually executed,
whereas the compare-exchange is the natural unit of work for the problem.

\section{Roofline model}
\label{sec:meth-roofline}

Execution time says how fast an implementation is, but not why it is not
faster. The roofline model~\cite{williams2009} answers this by comparing
each measurement against the two upper bounds imposed by the machine: a
bandwidth $\beta$ and a compute capability $\pi$. Which of the two binds
is a property neither of the machine alone nor of the algorithm alone,
but of their relationship, expressed by the operational intensity, the
ratio of operations $W$ to bytes $Q$ moved:
\[ I = \frac{W}{Q}, \qquad P = \min(\pi,\ \beta I) \]
Figure~\ref{fig:meth-roofline} shows how the resulting plot is read.

\input{figures/meth-roofline}

Applying the model here departs from usual practice in three respects,
all necessary for the comparisons to be honest.

First, both ceilings are measured on the same machine with separate
executables rather than taken from manufacturer datasheets, since what is
sought is what is actually achieved rather than what the hardware could
achieve ideally.

Second, the memory ceiling is not just a single number: achievable bandwidth
depends on the working-set size, since data arrives much faster while it
fits in some level of cache than from main memory. Bandwidth is therefore
measured over successive working-set sizes, starting at
\qty{32}{\kibi\byte} and doubling each time, and each measurement is
compared against the ceiling for its own working set. This scale
measures bandwidth under reuse, which might seem unsuitable for an
algorithm that traverses the input only once. Here, however, the input is
restored from its backup copy immediately before the timed region
(section~\ref{sec:meth-conditions}), so for working sets up to the last
cache level's size the data are already present in it and the measurement
corresponds to a second pass. Beyond that size, the scale converges on
its own to the rate of main memory.

Third, the compute ceiling is measured in compare-exchanges, for the
reason given in section~\ref{sec:meth-traffic}. If each compare-exchange
used the result of the previous one, the measurement would capture the
latency of a single operation rather than the rate at which many can
execute, and the ceiling would come out several times too low, with every
implementation appearing, incorrectly, to be touching it. The measurement
kernel therefore runs 64 independent chains in parallel, alternating
between three registers so no operation can be elided by the compiler.

For the neural processing unit the model carries a different meaning.
There is no available AIE kernel with tunable operational intensity, so
the measured ceilings concern the unit's feed path rather than tile
computation: they read as "how fast can the host prepare the data the
unit consumes," which is, in any case, the implementation's actual
bottleneck.

\section{Baseline libraries}
\label{sec:meth-baseline-libraries}

The performance baseline is an established library implementation per
architecture. A new implementation has value only if it is faster than
what a developer already has available.

For the processor, std::partial\_sort is used. Its choice over
std::nth\_element is not self-evident, but for k much smaller than n it
is clearly faster, since it maintains a heap of size k that stays in
cache and rejects most elements with a single comparison.

For the graphics unit, cub::DeviceTopK is used, which implements radix
selection. It is important that this is a genuine top-k selection
function and not a full sort followed by truncation, so the comparison
is against an opponent that solves the same problem in an optimised way.

For the neural processing unit there is no equivalent baseline: the AIE
toolchain provides a compiler and example kernels, not an algorithms
library, so no established top-k implementation exists for this hardware,
from the manufacturer or otherwise, to compare against. The same
std::partial\_sort used for the processor is used instead, running
entirely on the host without touching the unit at all. This changes the
question the comparison answers: not "is our implementation better than
an optimised AIE kernel," since no such kernel exists, but "is it worth
offloading the computation to the unit, or preferable to run it with the
means the host already has". This is the question anyone actually
considering its use faces in practice.

Sharing the baseline between the two architectures also provides an
independent check on the harness: because it is literally the same code
on the same hardware, the two measurements ought to agree, and their
agreement in chapter~\ref{ch:evaluation} confirms the harness introduces
no systematic bias depending on which architecture is declared.

\section{Correctness checking}
\label{sec:meth-correctness}

A timing measurement is meaningful only if the result is correct, so
every case of every sweep is verified, and failures are recorded as such
rather than included among the results.

Checking is done against a separate ground truth, not to be confused
with the baseline libraries of section~\ref{sec:meth-baseline-libraries}:
those are a performance baseline, this one judges correctness. It is the
simplest possible implementation: a copy of the input fully sorted on
the host, keeping the first k elements. It is slow, not meant to compete
with anything, and obviously correct enough that its verdict can be
trusted.

The comparison is not identical for all types: integer types require
exact equality, floating-point types a relative or absolute tolerance
depending on magnitude, since different architectures perform operations
in a different order and with different intermediate precision. Because
every implementation returns its result sorted, in the same order as the
ground truth (section~\ref{sec:bg-problem}), the comparison is made
position by position rather than as a set. When both
the full and the truncated network are run, the two results are
additionally cross-checked, confirming that truncation does not corrupt
the result.

In the main sweep of this work, all 2700 cases were verified with no
failures.

\section{Parameter space}
\label{sec:meth-parameters}

Each run is fully determined by its command-line parameters. None are
read from a configuration file or environment variable, so a
measurement's description is always complete and reproducible. The full
list is given in appendix~\ref{app:reproducibility}.

The input size is a power of two, n equal to $2^q$, with q swept from 3
to 24. The upper bound, about 16.8 million elements, is large enough that
the working set far exceeds the cache and the measurement concerns main
memory. The lower bound is not arbitrary, since for q smaller than 3 the
input has fewer elements than the smallest requested k.

The parameter k takes the values 8, 256, 4096, and 131072, orders of
magnitude apart, covering regimes from a k so small the heap fits in a
handful of registers to a k that is a significant fraction of the input
itself. Where k exceeds n, it is clamped to n.

\subsection{Input distributions}
\label{sec:meth-distributions}

The input distribution is not immaterial: heap-based algorithms perform
work only when a new element exceeds the heap's root, so the order in
which values appear drastically changes their running time. The five
distributions of table~\ref{tab:distributions} are swept. The executable
additionally supports the normal distribution, not used here since
trimodal covers clustered values more sharply. Each is shown in
figure~\ref{fig:meth-dists}.

The two ordered distributions form the two extremes for heap-based
selection (section~\ref{sec:bg-mapreduce}): descending is the most
favourable case and ascending the least. Adversarial preserves this
unfavourable behaviour without being fully sorted: most values lie in the
lower half of the range, with ascending spikes interspersed at regular
intervals.

Bitonic sort is data-oblivious, executing the same comparison network
regardless of the values, so it serves as a witness: if its time changes
across distributions, the change is due to the measurement, not the
algorithm.

\section{Measurement conditions and reproducibility}
\label{sec:meth-conditions}

The system is not, by default, in a state suitable for measurement: the
frequency governor is powersave and boost is active, so operating
frequency varies with load and temperature. This is a systematic drift
over the course of a sweep as the system heats up, not random noise, so
the standard deviation of samples taken under drifting conditions would
not capture the measurement's true uncertainty.

Before each sweep the system is therefore pinned to a fixed, documented
state, summarised in table~\ref{tab:conditions}, recorded before the
sweep and restored after. The corresponding commands are given in
appendix~\ref{app:reproducibility}.

\begin{table}[H]
    \centering
    \begin{tabular}{ll}
        \hline
        Parameter & State during measurement \\
        \hline
        CPU frequency governor & performance \\
        CPU frequency boost & disabled \\
        CPU threads & 8, one per physical core \\
        GPU persistence mode & enabled \\
        GPU power limit & fixed for the whole sweep \\
        Cool-down period between units & \qty{15}{\second} \\
        Warm-up repetitions & 5 per case \\
        Measured repetitions & 50 per case \\
        \hline
    \end{tabular}
    \caption{The conditions to which the system is pinned before each sweep.}
    \label{tab:conditions}
\end{table}

The graphics unit's power limit is chosen once, within the bounds of
table~\ref{tab:machine}, and held fixed throughout. Its specific value is
arbitrary, but any change to it during a sweep would alter time and
energy simultaneously.

As noted in section~\ref{sec:meth-machine}, the three units share a
common thermal budget. A \qty{15}{\second} cool-down between successive
units prevents each from starting from the thermal state left by the
previous one, and no other computational load runs during a sweep. This
is a mitigation rather than an elimination, since on a laptop the thermal
coupling between units cannot be removed, and this remains an
acknowledged limitation of the measurements.

Each case runs 5 times as warm-up and 50 times under measurement, with
mean, standard deviation, and minimum reported. Before each repetition
the input is restored from a backup copy, outside the timed region, so
the cost of the copy is not counted and every repetition starts from an
identical input. This is critical, since data-dependent implementations
would otherwise show artificially improved times on an already partially
sorted input.

Beyond the repetitions within a case, each combination of input
distribution and random-number-generator seed constitutes an independent
sample. The plots in this work aggregate these samples and depict their
spread as error bands, distinguishing uncertainty due to the data from
uncertainty due to the measurement.

Finally, each run records the environment in which it executed: the
repository revision, kernel, compiler, and each unit's driver and runtime
versions. This is stored alongside the results, so each set of
measurements documents its own production conditions independently of
external records that might drift out of sync.
