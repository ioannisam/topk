\section{Reference system}
\label{sec:meth-machine}

All measurements come from one single system, which carries all three
architectures. This isolates the differences between implementations from the
differences between platforms. The cost is that the system is a laptop, so the
three units share a common thermal and power budget.

The processor has eight physical cores with simultaneous multithreading. All
measurements use one thread per physical core, so that no two threads share the
same vector unit. The cache hierarchy sets the knee points of the measured
bandwidth scale (section~\ref{sec:meth-roofline}). Depending on the input size
and the data type, the working set may fit in L2, in L3, or only in main
memory, and each implementation is compared against the ceiling of its own
working set.

Main memory consists of two identical \qty{16}{\gibi\byte} modules in dual
channel, at 5600 MT/s. A single channel would halve the bandwidth, and a
memory-bound implementation would give worse results on an otherwise identical
system. This was confirmed in practice after upgrading the system memory from
one to two channels.

The neural processing unit has no memory of its own. It is fed from the same
DDR5, through the same memory controllers as the processor, on the same silicon
die, with two consequences that recur throughout this work. The cost of
preparing data on the host is not separable from the cost of the computation,
and the energy meter covers the whole package, not the AIE tiles individually
(section~\ref{sec:meth-energy}).

The entries of table~\ref{tab:machine} were measured directly on the system.

\section{Structure of the measurement harness}
\label{sec:meth-harness}

The harness is organised into four layers around one principle: the measurement
procedure itself is common to all architectures, and only the kernel differs.
The implementation itself does not affect how it is measured.

The first layer is the common C++ core, shared by all three implementations. It
reads the parameters and generates the input, schedules the layers of the
bitonic network and reads the energy meters. It then runs the warm-up and
measurement loop, checks correctness and prints the final report. All of this
happens in one place, so that the timing and energy measurements of every
architecture are defined by the same code.

The second layer holds the per-architecture executables, each with the same
interface for the three compared algorithms (bitonic sort, map-reduce with
local heaps, reference implementation), providing only the compute function
that the common measurement loop calls.

The third layer is the sweep driver. It enumerates the parameter space of
section~\ref{sec:meth-parameters}, runs each case in a separate process and
records its output verbatim together with its outcome. Each case starts from
clean memory, and if one fails the sweep carries on normally with the rest.

The fourth layer converts the raw results into tables and plots, embedding them
directly in the final report. There is no separate output path; the values in
the plots are by construction the ones the executable printed. The execution
environment is stored alongside the results (section~\ref{sec:meth-conditions})
and the commands of each stage are given in appendix~\ref{app:reproducibility}.
The structure is summarised in figure~\ref{fig:meth-harness}.

\section{Measured quantities}
\label{sec:meth-quantities}

\subsection{Measurement scopes: algo and end-to-end}
\label{sec:meth-energy-scope}

An accelerator may finish the computation very quickly and still lose to a
processor working in place, if it has to transfer the whole input to and from
main memory. Every case is measured in two scopes.

End-to-end covers the entire call from the host's side; everything required so
that, given an input in main memory, the result ends up there too. Algo covers
only the region in which the computation runs. Their difference is the cost of
heterogeneity itself, as summarised in table~\ref{tab:scopes} and in
figure~\ref{fig:meth-scopes}.

On the processor the two coincide by definition, since it is the accelerator
itself and there is no host cost to subtract.

The energy meter opens and closes at exactly the same points in the code as the
timer. Time and energy thus refer to the same region and are directly
comparable. A third, wider window around the entire measurement loop is also
recorded, as an upper-bound sanity check (section~\ref{sec:meth-energy}).

End-to-end is the fair scope for comparison across architectures, since it
includes the transfer cost for all of them. Algo omits the transfers, so it is
only useful for comparisons within the same architecture.

\subsection{Timing}
\label{sec:meth-timing}

The two scopes are not necessarily measured with the same mechanism. End-to-end
is always measured with a host clock, on either side of the call, by definition
the time perceived by the host. Algo is measured with whatever each
architecture provides for the region of its own computation.

On the graphics unit the measurement cannot be done with a host clock. Kernels
launch asynchronously and the call returns as soon as the kernel is placed in
the command stream, long before it finishes. Such a clock would measure the
launch, not the execution, and forced synchronisation would add its own cost.
Events within the command stream, timed by the device, are used instead.

On the neural processing unit there is no such device meter. Algo is defined
here by a host clock around the region of the offload. It measures allocating
and preparing buffers, dispatching jobs and the final merge of the partial
results. This quantity must be read as the cost of the entire offload; the
computation on the AIE tiles is only one part of it.

Each case is measured over fifty repetitions, with three quantities reported
per scope: the mean (the basis of the comparisons), the standard deviation (an
indication of stability) and the minimum (a lower bound). The meters have
nanosecond-scale resolution, against measured regions from a few tens of
microseconds to hundreds of milliseconds, so the cost of the timing itself is
negligible and is not subtracted.

\subsection{Energy measurement}
\label{sec:meth-energy}

The executable measures its own energy. An external tool would measure the
whole process, whereas the measurement loop occupies only part of it, a part
that differs systematically by architecture, introducing bias in favour of
those with lower initialisation cost.

The sources differ by architecture, but the scope stays symmetric. For all of
them the package energy is measured via RAPL, and for the graphics unit the
card's power is added. End-to-end thus corresponds to the total cost of solving
the problem for all three.

The sum, not the mean, of the fifty repetitions is reported. The RAPL counters
quantise each reading, but accumulate without reset. This is why the sum stays
accurate even when each individual difference is on the order of the
quantisation step.

The core subfield of RAPL recorded only \qty{6}{\watt} under full eight-thread
load, while package power rose by about \qty{53}{\watt}, a sign that it is
unreliable on this processor. This is why only the package subfield is used.

Three identical runs with the NVML counter gave energy values that differed by
more than a factor of four, while the time differed by only
\qty{0.2}{\percent}. The counter advances in steps of about \qty{20}{\joule}
every few tens of milliseconds, so bracketing a millisecond-scale kernel
returns an arbitrary multiple of the step, which makes it useless for the
graphics unit. Instead, a helper thread samples the card's instantaneous power
every \qty{2}{\milli\second} and integrates it over time. The reading itself
refreshes less often than the sampling period, so an algo window of a few
milliseconds relies on a reading that has not had time to refresh. Summing over
the 50 repetitions smooths out this inaccuracy, without eliminating it. The
RAPL counters, which refresh on a millisecond scale, do not have this problem.

Beyond the gross value, net energy is also reported: gross minus what the
system would consume idle over the same interval, with idle power measured
before every sweep. The net figure is preferable especially for the neural
processing unit, where the static consumption of the rest of the system
dominates, and for the graphics unit, where it cancels out the cost of the
sampling mechanism itself.

The package meter covers the entire die (host cores, NPU tiles, uncore, memory
controller, all under one shared meter). A run on the neural processing unit is
thus measured as the total energy of the system while it works, including data
preparation on the host. The comparison of the cost of solving the problem is
fair and symmetric, but it is not known how much energy the unit itself
consumes for the computation, since its own consumption is never separated from
that of the host. Isolating it would require external metering equipment.

\subsection{Data traffic measurement}
\label{sec:meth-traffic}

Every run also records the bytes it moved and the operations it performed,
which are the coordinates of section~\ref{sec:meth-roofline}. An error here
does not merely give imprecise numbers; it leads to an entirely wrong
conclusion about what limits the implementation.

Traffic is not estimated theoretically. It is counted directly by the code
where it occurs: per group of fused passes on the processor, per kernel launch
on the graphics unit, per data batch on the neural processing unit. The obvious
estimate, element count times type size, assumes every element is read once, an
assumption that does not hold here. Truncated bitonic sort traverses the
working set repeatedly, by a factor of roughly seven times the naive estimate
for k much smaller than n. The naive estimate would make every implementation
appear to use only a small fraction of the available bandwidth, wrongly leading
to the conclusion that none of them approaches the memory ceiling.

Wherever feasible, the count is checked by independent verification. For
bitonic sort with k up to 4096, the processor and the graphics unit run the
same layer schedule and compute their traffic in entirely separate code, yet
arrive at the same value down to the last byte, independent evidence that the
counting model is correct. For map-reduce the two values differ, as expected.
Although both maintain a local heap per thread, the processor runs few threads
while the graphics unit runs thousands, with a correspondingly larger working
space and an additional tree merge within each thread block, so the two
implementations genuinely move different volumes of data.

The accuracy of the count differs by algorithm, and every run itself states the
quality of its numbers. For bitonic sort the bytes and the operations are
exact, since the schedule is fully enumerable. For map-reduce both the bytes
and the comparison count are lower bounds, since the merge traffic and the
restoration of the local heaps depend on the data. For the reference
implementation both quantities are lower bounds, because the internal passes of
the libraries are not externally observable.

Operations are counted in compare-exchanges. Top-k selection performs no
arithmetic operations, so FLOPs have no meaning here.

\section{Roofline model}
\label{sec:meth-roofline}

Execution time alone does not explain why an implementation is not faster. The
roofline model~\cite{williams2009} answers this, comparing every measurement
against the two upper bounds of the machine: bandwidth $\beta$ and compute
capability $\pi$. Which of the two binds is a property of the relationship
between machine and algorithm, not of either one separately, and is expressed
by the operational intensity, the ratio of operations $W$ to bytes $Q$ moved:
\[ I = \frac{W}{Q}, \qquad P = \min(\pi,\ \beta I) \]
Figure~\ref{fig:meth-roofline} shows how it is read.

\input{figures/meth-roofline}

Applying the model here deliberately departs from usual practice, so that the
comparisons stay honest.

Both ceilings are measured on the same machine with separate executables, so
that they record what is actually achieved in practice.

The memory ceiling varies with the size of the working set, since data arrive
far faster while they fit in some level of cache than from main memory.
Bandwidth is therefore measured over successive sizes, starting at
\qty{32}{\kibi\byte} and doubling each time, and every measurement is compared
against the ceiling of its own size. This approach measures bandwidth under
reuse, which would seem unsuitable for an algorithm that traverses the input
once. That does not hold here, though: the input is restored from a backup copy
just before the timed region (section~\ref{sec:meth-conditions}), so for
working sets up to the size of the last cache level the data are already there
and the measurement corresponds to a second pass. Beyond that size, the scale
converges on its own to the rate of main memory.

The compute ceiling is measured in compare-exchanges, for the reason given in
section~\ref{sec:meth-traffic}. If every compare-exchange used the result of
the previous one, a dependency chain would form, measuring latency instead of
throughput, with a ceiling several times lower and every implementation wrongly
appearing to touch it. The measurement kernel therefore runs 64 independent
chains in parallel, alternating between three registers so that the compiler
does not elide any operation.

For the neural processing unit the model means something different, since there
is no AIE kernel with tunable operational intensity. The measured ceilings here
concern the feed path, not the computation on the tiles, and are read as ``how
fast the host can prepare the data the unit consumes'', which is the actual
limitation here in any case.

\section{Baseline libraries}
\label{sec:meth-baseline-libraries}

The performance baseline on each architecture is an established library
implementation, so that the comparison reflects the real benefit over what a
programmer already has available.

For the processor, std::partial\_sort is used. Choosing it over
std::nth\_element is not self-evident, but for k much smaller than n it is
clearly faster. std::partial\_sort wins because it maintains a heap of size k
that stays in cache and rejects most elements with a single comparison, whereas
std::nth\_element traverses large parts of the array repeatedly while
partitioning.

For the graphics unit, cub::DeviceTopK is used, which implements radix
selection. It is a genuine top-k function, that is, it does not fully sort and
then truncate. The comparison is therefore against an opponent that solves the
same problem in an optimised way.

The AIE toolchain provides a compiler and example kernels, not an algorithms
library, so no established top-k implementation exists for this hardware,
neither from the manufacturer nor from third parties. The same
std::partial\_sort of the processor is used instead, run entirely on the host
without any use of the unit. The question the comparison answers changes from
``is our implementation better than an optimised AIE kernel'' (no such kernel
exists) to ``is it worth moving the computation to the unit, or is what the
host already has preferable''.

The shared baseline also gives an independent check of the harness. Since the
same code runs on the same hardware, the two measurements ought to agree. Their
agreement in the results of chapter~\ref{ch:evaluation} confirms that the
harness introduces no systematic bias depending on the architecture.

\section{Correctness checking}
\label{sec:meth-correctness}

A timing measurement is meaningful only if the result is correct. Every case of
every sweep is verified, and those that fail are recorded as failures instead
of entering the results.

Checking is done against a separate verification implementation, which must not
be confused with the libraries of section~\ref{sec:meth-baseline-libraries}.
Those measure performance; this one judges correctness. It is the simplest
possible implementation: a copy of the input is fully sorted on the host and
the first k elements are kept. It is slow, with no intention of competing, and
only needs to be unquestionably correct.

The comparison is not the same for all data types. Integers require exact
equality, while floating-point types require a tolerance, relative or absolute
depending on the magnitude of the values, since different architectures perform
the operations in a different order and with different intermediate precision.
Every implementation returns its result sorted, in the same order as the
verification implementation (section~\ref{sec:bg-problem}), so the comparison
is made position by position, not as a set. When both the full and the
truncated network are run, the two results are also compared with each other,
which independently checks that truncation does not corrupt the result.

\section{Parameter space}
\label{sec:meth-parameters}

Every run is fully determined by command-line parameters, none from a
configuration file or environment variable. The description of a measurement is
thus always complete and reproducible. The full list is in
appendix~\ref{app:reproducibility}.

The input size n is a power of two, equal to $2^q$, where q takes values from 3
to 24. The upper bound, about 16.8 million elements, far exceeds the cache, so
the measurement concerns main memory.

The parameter k takes the values 8, 256, 4096, 131072, orders of magnitude
apart, from a k so small that the heap fits in a handful of registers to a k
that is a significant fraction of the input itself. Where k exceeds n, it is
clamped to it.

\subsection{Input distributions}
\label{sec:meth-distributions}

The distribution of the input values affects execution time. For instance,
heap-based algorithms do work only when a new element exceeds the root, so the
order in which the values appear drastically changes their time. Five
distributions are swept (table~\ref{tab:distributions},
figure~\ref{fig:meth-dists}). The executable also supports the normal
distribution, which is not used here since trimodal covers the case of
clustered values more sharply.

For heap-based selection (section~\ref{sec:bg-mapreduce}) the two ordered
distributions are the two extremes. Descending is the most favourable,
ascending the least favourable. Adversarial retains the unfavourable behaviour
without being fully sorted. Most of the values lie in the lower half of the
range, with ascending spikes at regular intervals.

Bitonic sort is data-oblivious, executing the same comparison network
regardless of the values, and so serves as a witness. Any change in its time
across distributions would betray an error in the measurement, since the
algorithm itself has no way of causing it.

\section{Measurement conditions and reproducibility}
\label{sec:meth-conditions}

By default the frequency governor is powersave and frequency boost is active.
The frequency varies with load and temperature, with a systematic drift over
the course of the sweep as the system heats up, not random noise. The standard
deviation of samples under such drifting conditions would not reflect the true
uncertainty.

So before every sweep the system is pinned to a fixed, documented state
(table~\ref{tab:conditions}), which is recorded before the sweep and restored
afterwards.

\begin{table}[H]
    \centering
    \begin{tabular}{ll}
        \toprule
        Parameter & State during measurement \\
        \midrule
        CPU frequency governor & performance \\
        CPU frequency boost & disabled \\
        CPU threads & 8, one per physical core \\
        GPU persistence mode & enabled \\
        GPU power limit & fixed for the whole sweep \\
        Cool-down period between units & \qty{15}{\second} \\
        Warm-up repetitions & 5 per case \\
        Measured repetitions & 50 per case \\
        \bottomrule
    \end{tabular}
    \caption{The conditions to which the system is pinned before every
    sweep.}
    \label{tab:conditions}
\end{table}

The graphics unit's power limit is chosen once, within the bounds of
table~\ref{tab:machine}, and kept fixed. Its value is arbitrary, but any change
during the sweep would alter time and energy at the same time.

The three units share a common thermal budget (section~\ref{sec:meth-machine}).
A \qty{15}{\second} cool-down period between successive units keeps each one
from starting from the thermal state of the previous one. This is, however,
only a partial remedy. On a laptop the thermal coupling between the units
cannot be fully removed and remains an acknowledged limitation of the
measurements.

Every case is run five times as warm-up and fifty times under measurement, with
the mean, the standard deviation and the minimum reported. Before every
repetition the input is restored from a backup copy, outside the timed region,
so that the cost of the copy is not counted and every repetition starts from an
identical input.

Every combination of distribution and random-number-generator seed is an
independent sample, beyond the repetitions within a case. The plots aggregate
these samples and depict their spread as error bands, uncertainty due to the
data as distinct from uncertainty due to the measurement.

Finally, every run records the environment in which it ran (repository
revision, kernel, compiler, driver and library versions of each unit). Every
set of measurements thus documents the conditions of its production without
depending on external records.
