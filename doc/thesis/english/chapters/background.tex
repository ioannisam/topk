\section{The top-k selection problem}
\label{sec:bg-problem}

\begin{definition}[Top-k selection]
\label{def:topk}
Given an array $A$ of $n$ elements from a totally ordered set and an integer $k
\le n$, find the subset of the $k$ largest elements of $A$.
\end{definition}

Although the final order of these elements is not part of the problem's
definition, every implementation in this work sorts them anyway before
returning them. The final sort costs $O(k \log k)$, negligible next to the
$O(n)$ of selection, and yields a single, checkable answer instead of one of
the many valid arrangements of the same set.

By its nature, the problem requires less information than sorting. Sorting
determines the relative order of all $n$ elements, whereas top-k selection is
satisfied with separating the set into two distinct parts: the $k$ largest
elements and the remaining $n-k$, regardless of their internal order. The lower
bounds confirm this; every comparison-based algorithm requires $\Omega(n \log
n)$ comparisons to sort, but only $\Theta(n)$ to select with fixed
$k$~\cite{knuth1998}. By sorting the entire input to keep k elements, an
implementation does more work than it needs to (figure~\ref{fig:bg-selection}).

\input{figures/bg-selection}

The distance between the two problems depends on the ratio $n/k$. For k much
smaller than $n$, selection is nearly linear and sorting wastes almost all of
its work. As k approaches $n$, the two problems coincide. The entire work moves
between these two extremes. Chapter~\ref{ch:evaluation} shows how the ranking
of the algorithms is overturned as this distance is traversed.

The problem appears everywhere. The search for the k nearest neighbours
requires selecting the smallest distances from a distance
matrix~\cite{sismanis2012}. Retrieval and recommendation systems return the k
best results of a query. In language models, top-k sampling and beam search
perform selection at every generation step. Although it is a small part of the
overall workload each time, it is a computation repeated so often that its cost
becomes noticeable.

\section{Selection algorithms}
\label{sec:bg-algorithms}

One criterion that divides selection algorithms into families is whether the
sequence of operations depends on the values of the data. An algorithm with a
fixed schedule executes the same operations in the same order regardless of the
input. A data-dependent algorithm adapts its course, doing less work on
favourable inputs and more on adverse ones.

This distinction corresponds to the established grouping of parallel selection
algorithms into sorting, partial sorting and partitioning
methods~\cite{zhang2023gputopk}. Beyond theoretical complexity, it determines
which hardware executes the algorithm efficiently, since parallel architectures
presuppose many processing elements executing the same instruction. It also
determines whether execution time is predictable.

\subsection{Bitonic sorting networks}
\label{sec:bg-bitonic}

A bitonic sorting network is a fixed sequence of comparators. Each comparator
takes two positions of the array, compares their contents and swaps them if
they are in the wrong order. Which positions it compares is fixed in advance,
independently of the values. It is a typical example of a data-oblivious
algorithm. The same sequence of comparisons is always executed; only the
outcome of each comparison changes.

The comparators are organised into layers. Within a layer, no position appears
in two comparators, so all of them can execute simultaneously. The layers,
however, follow one another, and their number is the depth of the network,
which defines the lower bound on time on unboundedly parallel hardware.

Batcher's construction rests on the bitonic sequence~\cite{batcher1968}, which
first increases and then decreases, or results from a cyclic shift of such a
sequence. A bitonic sequence of length $2m$ is sorted in $\log_2(2m)$ layers.
Comparing each element with the one $m$ positions away yields two bitonic
sequences of length $m$, where every element of the first is less than or equal
to every element of the second. The two halves are then sorted independently,
by the same procedure, recursively.

Full sorting of $n$ elements results from repeated application of the above
idea. Pairs of sorted blocks of opposite direction form a bitonic sequence of
double the length, which is sorted to give a block of double the size. The
network has $\log_2 n \, (\log_2 n + 1)/2$ layers and $n/2$ comparators per
layer ($O(n \log^2 n)$ in total), a factor of $\log n$ more than the $O(n \log
n)$ of sequential sorting algorithms. In exchange it offers fully
predetermined, uniform comparisons, without any control-flow divergence. This
runs equally well on vector units, on SIMT, or on dataflow arrays, which is why
it remains competitive on parallel hardware despite its asymptotic
disadvantage.

\subsection{Truncated bitonic sort}
\label{sec:bg-truncated-bitonic}

Truncated bitonic sort discards elements as soon as it is proven that they
cannot belong to the result~\cite{sismanis2012}. The same idea, halving the
active array at every step, also underlies partial-sorting implementations for
graphics units~\cite{shanbhag2018}.

Let $k'$ be the smallest power of two greater than or equal to k. The procedure
has two phases. In the first, ordinary bitonic sort is executed, but it stops
as soon as sorted blocks of size $k'$ are formed (not at the single block of
size $n$). In the second, the blocks are merged in pairs, and of the $2k'$
elements of each pair only the $k'$ largest are kept, while the rest are
discarded permanently. This step halves the size of the active array and
repeats until a single block remains, which contains the desired result.
Figure~\ref{fig:bg-bitonic} contrasts the two structures. The correctness of
the discarding is immediate. If an element does not belong to the $k'$ largest
of two sorted blocks, $k'$ elements larger than it already exist in the array,
so it does not belong to the $k$ largest of the set either.

The first phase needs $\log_2 k' \, (\log_2 k' + 1)/2$ layers, a count that now
depends on k, instead of $\log_2 n \, (\log_2 n + 1)/2$. The second is applied
to an array that shrinks geometrically, so its cost sums to a term linear in
$n$. The overall complexity falls from $O(n \log^2 n)$ to $O(n \log^2 k)$.

For example, with $n = 2^{24}$ and k equal to 8, the full network has 300
layers and 2\,516\,582\,400 comparators, while the truncated one has 90 layers
and 92\,274\,668 comparators, that is, twenty-seven times fewer. In contrast,
for $k = 131072$ it requires 279 layers and 1\,441\,595\,392 comparators, only
1.7 times fewer than the full network. The benefit of truncation shrinks as k
grows.

The total number of comparators in the truncated network is given by
\[
	\frac{n}{2} \cdot \frac{\log_2 k' \, (\log_2 k' + 1)}{2}
	+ \frac{(\log_2 k' + 2)(n - k')}{2},
\]
where the first term corresponds to the first phase and the second to the
merge-and-truncate step.

Truncation preserves data-obliviousness. The schedule of layers is computed in
advance from n and k alone, so how many elements are discarded at each step is
known in advance, even if which ones depends on the values.

\subsection{Selection with heaps and map-reduce}
\label{sec:bg-mapreduce}

Selection with heaps follows a different logic from sorting networks. It does
not impose a fixed schedule; it maintains a structure with the k largest
elements examined so far and updates it only when necessary.

The structure is a min-heap of capacity k. Its root holds the smallest of the k
current best elements and acts as a threshold. Each new element is compared
with the root in a single comparison and, if it does not exceed it, is
discarded with no further work. Otherwise it replaces the root, and the heap is
restored in $O(\log k)$ steps.

On random input the threshold rises quickly and the overwhelming majority of
elements are discarded with one comparison, so the time approaches linear. On
ascending input, however, every new element exceeds the root and forces a
restoration, giving $O(n \log k)$ in the worst case.

Parallelisation follows the map-reduce scheme (figure~\ref{fig:bg-heap}). In
the map phase the input is partitioned and each worker maintains its own local
heap, without synchronising with the others, and in the reduce phase the
partial results are merged into one. The scheme is attractive because the map
phase requires no communication. Each local heap must first fill with k
elements before it can start filtering, so the number of workers that actually
contribute does not exceed the ratio $n/k$. On a processor with eight threads
this limit goes unnoticed, but on a graphics unit with thousands of threads it
becomes the main limiting factor, as analysed in
section~\ref{sec:gpu-mapreduce-limit}.

\subsection{Radix selection}
\label{sec:bg-radix}

Radix selection examines the binary form of the values instead of comparing
them directly. The values are distributed into buckets according to a group of
digits. The bucket counts are summed, and from them it follows which bucket
contains the k-th largest element. The buckets above it belong entirely to the
result, those below it are discarded entirely, and the search continues only
within the critical bucket, with the next group of digits
(figure~\ref{fig:bg-radix}).

The number of passes is determined solely by the width of the data type. This
is why the method has no collapse point as k grows. Each pass is, moreover, a
sequential read with frequency counting, a pattern well suited to
high-bandwidth architectures.

The method is also data-dependent, but in a different way from heaps: here the
time depends on the distribution of digits in the values. When many elements
share the same significant digits, the critical bucket narrows slowly and more
passes are needed; this is the radix-adversarial distribution known in the
literature, addressed with adaptive candidate-storage
strategies~\cite{zhang2023gputopk}. This family was not implemented in the
present work, but it is used as the basis of the graphics unit's reference
library (section~\ref{sec:bg-related}).

\section{Processing architectures}
\label{sec:bg-architectures}

The three architectures expose parallelism in different ways.

\subsection{CPU vector extensions}
\label{sec:bg-arch-cpu}

The modern general-purpose processor combines two forms of parallelism:
multiple threads, each with its own independent instruction stream, and vector
extensions, which apply the same operation to many data items simultaneously
within one thread.

An AVX-512 register is 512 bits wide, that is, sixteen 32-bit integers. Beyond
arithmetic operations, the repertoire includes shuffle instructions, which
permute elements within the register, and min/max instructions, which select
element-wise without branching. The combination of shuffle, min and max is
equivalent to one sorting-network comparator. Bitonic sort is a natural
candidate for vectorisation.

Data supply usually becomes the limit first, before the rate of operations has
a chance to become a problem. The cache hierarchy compensates for the speed gap
with main memory, but only for algorithms that reuse data while it remains at a
nearby level.

\subsection{The SIMT model and GPU memory hierarchy}
\label{sec:bg-arch-gpu}

The graphics unit is organised around the SIMT model. Threads are grouped into
warps that execute the same instruction on different data. When the threads of
a warp follow different branches, the branches execute serially with the
inactive threads disabled. Control-flow divergence therefore has a direct cost,
and branch-free algorithms have the advantage.

Warps are grouped into thread blocks, and blocks into a grid. Each block has
shared memory, a small region managed explicitly by software, with latency far
lower than that of global memory. With it, a multi-pass algorithm is turned
into a single-pass one. If the chunk of data processed by a block fits there,
all intermediate steps execute without returning to global memory.

Access to global memory is efficient only when the threads of a warp request
consecutive addresses, so that the individual requests are coalesced into few
transactions. Finally, the graphics unit is a discrete device. Data must be
transferred to and from its memory over a bus whose bandwidth is an order of
magnitude lower than that of local memory.

\subsection{The AIE dataflow architecture}
\label{sec:bg-arch-npu}

The term neural processing unit has meant different things in different eras.
The first proposals targeted approximate computation to save
energy~\cite{palmer2014npu,esmaeilzadeh2012}. Dedicated neural-network
accelerators followed~\cite{chen2014diannao}, whose performance-per-watt
advantage was established when they were deployed at data-centre
scale~\cite{jouppi2017tpu}.

According to the Eyeriss design principle, moving a piece of data costs orders
of magnitude more energy than the operation that will be performed on it, so
design is organised around maximising local data reuse~\cite{chen2016eyeriss}.
In convolution and matrix multiplication this assumption is fully vindicated,
since every element loaded participates in many operations. In top-k selection
each element is examined a minimal number of times, so the same assumption does
not hold.

The architecture examined belongs to AMD's AI Engine family, introduced with
the Versal adaptive systems~\cite{amd2021versal} and later integrated, as XDNA,
into general-purpose processors~\cite{amd2024xdna}.

The execution model is spatial, fundamentally different from the previous two.
The unit consists of an array of tiles, each with its own vector processor and
its own local memory. There is neither shared memory nor cache memory, so
communication happens exclusively through explicit data transfer over an
interconnect network.

The program is therefore expressed as a graph of compute kernels connected by
streaming channels, instead of a sequence of operations on a shared address
space. The programmer describes which tiles execute which kernel and how data
flows between them. The abstraction this work uses for this purpose is the
object\_fifo of the MLIR-AIE framework~\cite{mliraie}, presented in
section~\ref{sec:npu-objectfifo}.

The local memory of each tile is small and fixed in size, so the computation
must be split into chunks that fit there, with the partial results merged
elsewhere. Moreover, feeding the array remains the responsibility of the host.
It has to prepare and forward every chunk. When the computation per element is
small, as in selection, the cost of feeding dominates over the cost of
computation.

\section{Existing implementations and libraries}
\label{sec:bg-related}

The availability of ready-made implementations is not the same across the three
architectures, and this disparity shapes both the question of this work and the
choice of baselines in section~\ref{sec:meth-baseline-libraries}.

For the processor, the C++ standard library offers std::nth\_element, which
partitions the array around the k-th element in expected linear time, and
std::partial\_sort, which additionally sorts the result by maintaining a heap
of size k. Both are available everywhere and well tested, but strictly
single-threaded, exploiting neither multiple threads nor vector extensions.

On the graphics unit, CUB, part of the CCCL library collection~\cite{cccl},
provides DeviceTopK, a radix selection implementation as described in
section~\ref{sec:bg-radix}. It is a mature and highly optimised solution, which
this work uses as a baseline, without aiming to surpass it across the entire
parameter range.

How strongly the choice of algorithm depends on k is recognised in industry
too. Recent work on AMD graphics units records exactly the same overturn
described in section~\ref{sec:eval-time-k} and addresses it with an adaptive
strategy; register-level bitonic sort for small k and radix selection for large
k, with an empirically determined transition point~\cite{lin2026adaptivetopk}.

Alongside exact methods there is also a line of approximate algorithms, which
trade recall for speed and mainly target machine-learning workloads, where
top-k selection proves to be a systematic bottleneck on accelerators designed
for dense matrix multiplication~\cite{samaga2026}. The present work is
restricted to exact selection.

For the neural processing unit no equivalent library exists: its ecosystem is
oriented towards neural-network operators and does not include a top-k
selection primitive. The closest available material is an official bitonic sort
example on an AI Engine tile~\cite{amd2024bitonicaie}, which, however, performs
full sorting, only for single-precision numbers, and only for sizes up to 1024
elements that fit in the local memory of one tile. The gap the present work is
called to fill is exactly this: selection instead of sorting, five data types
instead of one, and inputs of up to $2^{24}$ elements that require pipelining
across multiple tiles.

Every implementation must be built from scratch at the level of
MLIR-AIE~\cite{mliraie}, which makes this unit the most demanding part of the
work. Moreover, there is no natural on-device baseline, so this work uses the
host implementation as the reference, a choice justified in
section~\ref{sec:npu-reference}.

The literature on top-k selection for graphics units is extensive overall,
covering both sorting networks and radix-based
methods~\cite{sismanis2012,lin2026adaptivetopk}. In contrast, the corresponding
literature for AIE-type dataflow accelerators is limited, since these units are
recent and their use focuses on convolution and matrix-multiplication
workloads.
