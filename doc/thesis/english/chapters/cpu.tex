\chapter{CPU implementation}
\label{ch:cpu}

\section{Design choices}
\label{sec:cpu-design}

The two implementations of this chapter share a common design basis: they
vectorise the compare-exchange instead of staying with scalar code, and they go
through a common abstract interface instead of being written as near-identical
copies. In addition, they convert half precision to single precision for the
computation, while the distribution of threads differs between the two.

\subsection{Vectorisation}
\label{sec:cpu-simd}

Both algorithms rely on an operation that vectorises exceptionally well. The
compare-exchange of two elements is equivalent to computing the minimum and the
maximum, and both exist as instructions that act on an entire vector register
at once, without branches. A 512-bit register performs sixteen single-precision
integer comparisons in the time of one. The instructions are referred to here
by the names of the intrinsic functions of the standard~\cite{intelintrinsics}.

The comparison itself is simple; the difficulty lies in positioning. To compare
two elements that are $j$ positions apart, they must end up in the same
position of two different registers. When $j$ is smaller than the register
width, this is done by shuffling within the register. The contents are shifted
by $j$ positions, the minimum and maximum are computed, and the result is
reassembled by alternately selecting from the two with a mask. The sequence
``shuffle, minimum, maximum, select'' is the basic motif on which the layer
fusion of section~\ref{sec:cpu-bitonic} is built
(figure~\ref{fig:cpu-simd-motif}).

\input{figures/cpu-simd-motif}

The register width is not known at compile time. The code is compiled with all
paths present. The choice is made at start-up, by querying the processor for
the instructions it supports. If it supports AVX-512 it selects 512-bit
registers, otherwise 256-bit ones, and otherwise, as a fallback, a scalar path.
The same executable therefore runs on any machine, with the difference that on
different hardware it follows a different code path and its results are not
directly comparable.

\subsection{Vector type abstraction}
\label{sec:cpu-simd-traits}

Vector instructions are specialised by data type. One instruction is used for
the minimum of signed integers, another for unsigned, another for floating
point. Five types times two register widths times two algorithms: writing the
code directly would give twenty nearly identical variants, with the
corresponding maintenance cost.

To avoid this, a single interface is defined. For each combination of type and
width a structure is declared that always exposes the same names (vector type,
width in elements, load, store, minimum, maximum, masked select, shuffle,
generation of the candidate mask for map-reduce). The algorithms are written
once against it, without ever referring to a specific instruction.

Adding a new type needs only a specialisation of the structure, no change to
the algorithms, and a missing specialisation shows up immediately at compile
time. Without a declared interface for some combination, the code automatically
falls back to the scalar path. The equivalence of the paths is tested.

\subsection{Half-precision floating-point support}
\label{sec:cpu-fp16}

The processor stores 16-bit values without having arithmetic instructions that
act directly on them at the width the algorithm needs. Scalar processing would
negate any benefit. The solution exploits the fact that conversion between the
two representations takes a single instruction. The half-precision
specialisation of the interface defines its vector type as that of single
precision. The load reads sixteen 16-bit values and converts them to sixteen
32-bit ones, all operations execute in single precision, and the store converts
them back. The data stay in half precision in memory and become single
precision only for the duration of the computation (figure~\ref{fig:cpu-fp16}).

\input{figures/cpu-fp16}

Every half-precision value is represented exactly in single precision, and the
minimum/maximum operations simply select one of the two inputs, with no
approximation or rounding involved. The result is identical to that of an
implementation that would work natively in half precision.

The register width in elements remains sixteen, the same as for single
precision, so the rate of comparisons does not change. Data traffic, however,
is halved, and each element occupies half the bytes. For memory-bound
algorithms this translates directly into a speed-up.

\subsection{Parallelisation across multiple threads}
\label{sec:cpu-threads}

The two algorithms are parallelised in fundamentally different ways, and the
difference determines how aggressively each one scales.

Bitonic sort has global dependencies. Each group of layers needs the result of
the previous one to be complete. Parallelism is possible only within the
groups, with a synchronisation barrier between them.

Map-reduce has a different structure. The threads are entirely independent on
disjoint segments and meet once, at the merge. No synchronisation is required
during the scan, but each thread keeps its own heap of size k, and the final
merge is serial, proportional to the number of threads.

The optimal number of threads therefore differs. Bitonic sort tolerates more of
them on smaller inputs; map-reduce needs a much larger share per thread to
amortise the cost of the extra heap and the serial phase. In both cases the
count is limited dynamically according to the input size.

\section{Bitonic sort}
\label{sec:cpu-bitonic}

The layer schedule of section~\ref{sec:bg-truncated-bitonic} is built once and
is shared by all three architectures. However, translating it directly into
code gives an implementation that is hopelessly memory-bound. For k equal to
256, the first phase alone has 36 layers, 36 separate passes over the entire
array. On an input of four million elements this means dozens of consecutive
sixteen MB reads and writes, with minimal computation in between. The
implementation is organised around avoiding this pattern.

The basic technique is fusing consecutive layers into one pass. A layer is
characterised by the distance $j$ between the elements it compares, and this
determines what is feasible. For $j$ smaller than the register width, the two
elements of each comparison are already in the same register. A whole sequence
of such layers then executes as one load, a series of shuffles and comparisons,
and a store. For larger $j$, but a working set that fits in cache, the sequence
runs chunk by chunk, staying there for all the layers. Only layers with very
large $j$ need a separate pass. A truncation layer with a distance equal to the
register width also absorbs the re-sort layers that follow it
(figure~\ref{fig:cpu-layer-fusion}). When the parameters of a layer fall
outside the supported range, the same sequence runs in scalar instead of vector
form. The output range of each group is divided among the threads, with
boundaries aligned to the chunk size or the cache line, so that two threads
never write to the same line.

\input{figures/cpu-layer-fusion}

The resulting traffic is predictable from the structure of the schedule. The
first phase collapses into one in-place pass, that is, one read and one write
per element, $2n$ in total. Each step of the second reads $n_i$ elements and
writes $n_i/2$, and the re-sort that follows adds another $2 \cdot n_i/2$, a
total of $2.5\,n_i$. And since $n_i$ halves at every step, the sum is a
geometric series:
\[
	\sum_i 2.5\,n_i = 2.5 \left( n + \frac{n}{2} + \frac{n}{4} + \cdots \right) = 2.5 \times 2n = 5n.
\]
About $7n$ elements in total. This is the origin of the repetition factor of
section~\ref{sec:meth-traffic}. For $n = 2^{22}$, k equal to 256, this gives
117\,435\,392 bytes, exactly the measured value.

The truncation layers do not run in place, since each output element results
from two input elements at different positions. A second array of the same size
is maintained, with the two swapped after each such group. The extra memory is
the price for avoiding intermediate copies.

\section{Map-reduce with local heaps}
\label{sec:cpu-mapreduce}

Here an entirely different logic is followed. Instead of a fixed sequence of
comparisons, the k best elements examined so far are maintained and every new
one is tested against them. The input is split into segments, one per thread,
and each thread produces its own k best. The partial results are merged at the
end.

Each thread maintains a heap of size k, with the worst of the selected elements
at the root. Each heap is bulk-initialised from the first k elements of the
segment, which costs linearly and is cheaper than k successive insertions. From
then on, the root acts as a threshold: any element that does not exceed it can
be rejected with no further work.

This rejection happens in bulk. The threshold is broadcast into a vector
register and compared simultaneously against an entire block of elements,
producing a binary mask of candidates. The implementation examines four such
blocks together and, if the union of the four masks is zero, skips all of them
with one check. When the heap has already filled with large values (the usual
case), most of the input passes through exactly like this: read, compared and
rejected, without any element being examined individually
(figure~\ref{fig:cpu-mapreduce-reject}).

\input{figures/cpu-mapreduce-reject}

Scalar work runs only for the bits that are actually set. The root is replaced
and the heap is restored by sifting down. Replacing the root is preferred over
extraction and reinsertion, since the latter would traverse the heap twice
instead of once.

This is where the data dependence of section~\ref{sec:meth-distributions} comes
from. On descending input the heap fills immediately with the largest values,
the threshold rises to its maximum from the start and all the rest of the input
is rejected in bulk. On ascending input the opposite happens: every new element
exceeds the root, no mask is zero and every element forces a full sift-down.
The same code, on an input of the same size, thus performs almost no work
beyond reading in one case and the maximum possible in the other, the only
difference being the order in which the values appear.

The merge is simple and serial. The elements of each local heap are offered in
turn to the first one, with the same threshold criterion, and the final result
is sorted. The cost is proportional to the product of threads and k and
independent of the input size, hence negligible for large n.

Data traffic follows directly. Every input element is read exactly once, and
the merge moves twice the product of threads and k. The comparison count,
however, is reported as a lower bound, since the depth of each sift-down
depends on the values. The count records one comparison per element and ignores
the restoration of the heap.

The thread count is limited far more conservatively than in bitonic sort. It
needs about one million elements per thread (a limit found empirically),
because every additional thread adds a heap of size k and burdens the serial
merge. For four million input elements, four threads are used rather than
eight, even when eight are requested.

\section{Memory management and data traffic}
\label{sec:cpu-memory}

The two algorithms solve the same problem on the same machine, but with
entirely different memory behaviour. Most of the performance difference comes
from there.

The fundamental difference is, first, the volume of traffic. From the
expressions of sections~\ref{sec:cpu-bitonic} and~\ref{sec:cpu-mapreduce},
bitonic sort moves about $7n$ elements, while map-reduce moves $n$ plus a term
proportional to threads times k, negligible for small k. For an input of four
million integers, the first moves 117 MB and the second 17 MB.

The nature of the access matters just as much. Map-reduce reads the input and
never touches it again, purely sequential reading, the most favourable pattern
for the prefetcher. Bitonic sort, by contrast, writes on every pass, with
comparisons between elements a variable distance apart, at some layers larger
than what fits in cache.

The footprint also differs. Bitonic sort needs a second array equal in size to
the first, $2n$ elements in total. Map-reduce allocates only the local heaps,
that is, threads times k elements, independent of the input size. For small k
this is small enough to stay permanently in the fastest levels of the
hierarchy, with the only traffic to main memory being the reading of the input
itself.

Relative to the ceilings of section~\ref{sec:meth-roofline}, the two algorithms
thus end up at different points. Both perform few operations per byte, so
neither approaches the compute ceiling. Map-reduce achieves a substantially
higher transfer rate, as expected from its more favourable access pattern.
Bitonic sort pays twice, because it moves a sevenfold volume and at a lower
rate.

This advantage, however, does not hold across the whole range of k. The term of
the local heaps grows with k and for the largest values stops being negligible.
The heap no longer fits in the fastest cache levels, and the serial merge
acquires a weight comparable to the scan. Bitonic sort, with traffic that
depends much more weakly on k, has no equivalent penalty.

\section{Reference implementation}
\label{sec:cpu-reference}

The baseline for the processor is std::partial\_sort from the standard library
(section~\ref{sec:meth-baseline-libraries}). It is integrated into the same
harness, the same measurement loop and the same correctness check as the two
implementations of this work. As a result, the times are directly comparable.

There is, however, an asymmetry that affects the speed-up measurements. The
library function is strictly single-threaded; it accepts no thread-count
parameter and uses only one core. In contrast, bitonic sort uses up to eight
threads and map-reduce four or eight, depending on the input size. Any
difference in performance between the implementations of this work and the
library is therefore due to two factors at once: the algorithmic differences
and the unequal number of cores.

The practical speed-up over the standard solution the programmer already has
available remains, however, the central question, and that solution is indeed
single-threaded. The reader should bear in mind that a stricter
thread-for-thread evaluation would give smaller speed-ups.

\section{Limiting factors}
\label{sec:cpu-bottlenecks}

The limiting factor is not the same across the whole range of k. In fact, this
shift is so decisive that it changes which of the two implementations is
faster.

For small k and large input, both implementations are clearly memory-bound. At
the largest input examined, bitonic sort reaches four-fifths of the measured
bandwidth ceiling and map-reduce three-quarters, with compute-ceiling
utilisation around five percent for both. The limitation here is memory.

This diagnosis sets the bounds of any possible improvement. Bitonic sort does
not execute its comparisons inefficiently. It is slow because it moves a
sevenfold volume, and no optimisation of the kernel would speed it up
substantially. Map-reduce already reads every element exactly once, close to
the rate at which memory can feed it, essentially optimal, in the sense that it
cannot get faster without reading less.

For large k the picture changes radically and neither implementation approaches
either ceiling. At the largest value of k examined, utilisation falls to
figures on the order of one percent for map-reduce and a little above ten
percent for bitonic sort. When a measurement is far from both ceilings, the
real limitation shifts from bandwidth or compute capability to latency and
insufficient parallelism.

As for map-reduce, as k grows the heap's threshold falls and the rejection rate
collapses. The fast path that skips four blocks stops activating and almost
every element forces a full sift-down. At the same time the heap stops fitting
in the fastest cache levels, so every sift-down becomes a sequence of
random-address accesses, of depth logarithmic in k. The algorithm thus turns
from bandwidth-bound to latency-bound, and at the largest value of k it ends up
slower than bitonic sort.

A secondary but real factor is the thread-scaling limits. Because map-reduce
needs about one million elements per thread, at medium input sizes only part of
the available cores work. Part of the gap from the ceiling there is simply due
to the whole processor not working.
