\chapter{Conclusions and future work}
\label{ch:conclusions}

\section{Conclusions}
\label{sec:concl-summary}

This work implemented two top-k selection algorithms on three
architectures and measured them over the same parameter space, with a
common harness and common correctness checking. The conclusions that
follow do not repeat the measurements of
chapter~\ref{ch:evaluation}, but rather what generalises from them
beyond the specific hardware.

\paragraph{Top-k selection is a data-traffic problem.}
For small $k$, every combination of algorithm and architecture is
limited by bandwidth rather than by the devices' computational
capability (section~\ref{sec:eval-roofline}). Performance depends
solely on reducing the volume of data moved, not on speeding up the
computation. Bitonic sort on the graphics unit confirms this clearly:
although it makes use of a larger fraction of its bandwidth ceiling
than the reference library, it still loses, because it is forced to
move several times as much data.

\paragraph{The appropriate algorithm is determined by the ratio $n/k$,
not by the architecture.} The fastest implementation for $k$ equal to 8
is the slowest for $k$ equal to 131072 regardless of platform
(section~\ref{sec:eval-time-k}), while the sorting network's
performance stays far more stable. The cause is structural rather than
implementation-specific: the heap only begins to filter once it is full,
so the available parallelism is capped by the ratio $n/k$. Similar
behaviour has also been observed in the
literature~\cite{lin2026adaptivetopk}, underscoring the need for
algorithms that adapt to the input data.

\paragraph{The measurement boundary determines which architecture
``wins''.} In the algorithmic scope the graphics unit is faster only at
the two extremes of the size range; in the end-to-end scope the
processor is faster across the entire range, including those same
extremes. The ranking, that is, overturns exactly where the graphics
unit appeared to win, and the only difference between the two answers is
where the measurement boundary is placed. This finding has methodological
significance beyond the specific problem: any speed-up claim for
offloading to an accelerator that reports only kernel time is not
verifiable, because it conceals precisely the cost that determines
whether offloading is worthwhile.

\paragraph{Power and energy.} The neural processing unit has the lowest
power draw of any implementation and at the same time the highest
energy consumption, since duration dominates the product
(section~\ref{sec:eval-energy}).

For top-k selection with small values of $k$, offloading the
computation to an accelerator proves disadvantageous in both energy and
time compared to running map-reduce on the processor. Architectures
such as NPUs (section~\ref{sec:bg-arch-npu}) presuppose high local
reuse of data to amortise the cost of moving it. Top-k selection offers
no such reuse, so most of the time ends up spent preparing the data,
leaving the device idle (section~\ref{sec:npu-pipeline}).

The sole exception is bitonic sort on the neural processing unit for
half-precision numbers, where it outperforms the corresponding
reference implementation. The advantage is attributable to the
processor library's poor optimisation for this particular data type
(section~\ref{sec:eval-dtypes}).

\section{Limitations}
\label{sec:concl-limitations}

The most significant asymmetry concerns the processor's baseline.
std::partial\_sort is strictly single-threaded, whereas this work's
implementations exploit parallelism, so every ratio of times between
them conflates two causes, the difference in algorithm and the
difference in thread count, as already noted in
section~\ref{sec:cpu-reference}. This choice is justified by
the question this work asks, which concerns comparison with what the
programmer already has available; the reader should nonetheless bear
it in mind.

The measured data traffic of the reference implementations is a lower
bound rather than an actual measurement, since only the input and output
are counted while the libraries' internal passes are not observable.
Every ceiling-utilisation percentage reported for them in
section~\ref{sec:eval-bandwidth} is consequently an underestimate.

For the neural processing unit there is no on-device baseline, because
no top-k selection library exists for that architecture. The reference
implementation runs on the host, so the relevant comparisons answer the
question ``is offloading worthwhile'' rather than ``how good is the
implementation relative to the best possible one on the device''.
Correspondingly, the phase-breakdown analysis in
section~\ref{sec:npu-pipeline} comes from separate runs with debug mode
enabled rather than the standard sweep, so its percentages rest on a
smaller sample of repetitions than the rest of the measurements in
appendix~\ref{app:reproducibility}.

Finally, the experimental space was limited to a single system and
specific ranges of values. The qualitative trends -- in particular the
dependence on the ratio $n/k$ and the role of the measurement boundary
-- are expected to generalise to comparable systems; the exact
numerical factors, however, remain closely tied to this particular
test platform.

\section{Future work}
\label{sec:concl-future}

In terms of systematic optimizations, the execution of multiple simultaneous
\tl{top-k} queries is the primary future extension, especially for the neural
processing unit. Since the main bottleneck lies in the preparation and
dispatch of data, batching the calls would crucially help amortize this cost.
Such repeated queries dominate the applications of Section~\ref{sec:bg-problem}.
In the same direction, leveraging direct memory access mechanisms of the
device to the system memory, avoiding explicit data copying from the \tl{host},
would significantly improve total latency. The implementation of such a
capability depends largely on the specifications and interfaces of the
respective platform.

Regarding algorithmic extensions, a dynamic algorithm selection mechanism
would directly exploit the finding on the $n/k$ ratio. Knowing now how the ratio
affects performance, an adaptive implementation could automatically choose
between a heap and a sorting network to ensure smooth performance across the
entire range of sizes. Furthermore, for larger values of $k$ where selection
approaches full sorting, managing inputs that do not fit in device memory
represents a natural continuation, transforming flow management from a
responsibility of the infrastructure into an organic part of the algorithm itself.

Finally, the evaluation framework developed in this work can be reused in
the future for studying other computational loads as well. The separation of
algorithmic time from transfer time, the unified energy logging across different
architectures, and the analysis via the roofline model offer a reusable
framework capable of being applied to any other problem considered for
offloading to specialized hardware.
