\chapter{NPU implementation}
\label{ch:npu}

\section{Design choices}
\label{sec:npu-design}

The neural processing unit is a radically different architecture from the two
previous ones. It does not execute a program in the usual sense, because it is
an array of tiles configured in advance, with no cache, no dynamic memory
allocation and no ability to change its dataflow at run time.

On the processor and the graphics unit the question was how the algorithm is
distributed across threads. Here the question is what small, fixed piece of
work the array executes efficiently and how the host feeds it without
interruption.

\subsection{Development flow with MLIR-AIE}
\label{sec:npu-toolchain}

There is no programming environment equivalent to that of the graphics unit.
This work relies on MLIR-AIE~\cite{mliraie} and the IRON interface~\cite{iron}.
Development requires two separate artefacts, from different toolchains, which
are combined at the end.

The first describes the array itself: which tiles are used, which channels
connect them, with what pattern data moves to and from main memory. It is
written in a domain-specific language embedded in Python, translated into an
intermediate representation and finally into a binary hardware configuration
file. The second is the compute kernel of each tile, written in C++ with the
architecture's vector primitives and compiled separately.

The configuration is fixed at compile time. The topology, the sizes of the
intermediate buffers, the transfer pattern, are all decided before each run,
independently of the parameters of the problem. Changing k or the input size
changes nothing on the device, only the way the host splits the input and
interprets the results.

\subsection{Tile topology and object\_fifo}
\label{sec:npu-objectfifo}

The array is organised into columns. Each column has a shim tile that
communicates with main memory and, above it, compute tiles.

Data transfer is not programmed with explicit copy instructions; it is declared
as a channel between two tiles. Each channel is backed by a number of
intermediate buffers, here two, so as to allow overlap: while the tile
processes one, the direct memory access mechanism fills the other. Without
this, every tile would stall on every transfer. This technique is known as
double buffering.

Each compute tile has its own pair of channels to the shim tile of its column,
one for input, one for output. There is no communication between compute tiles,
which is a deliberate choice. The work assigned to them is by definition
independent per tile and no exchange is required.

The amount of data per dispatch follows from the product of the above
(figure~\ref{fig:npu-topology}). Each tile receives chunks of 1024 elements,
128 such chunks per dispatch, so the batch size scales with the number of tiles
the algorithm in question uses. Larger inputs are split into successive
batches.

\section{Bitonic sort}
\label{sec:npu-bitonic}

An essential difference affects all the measurements: the array departs from
the truncated bitonic sort schedule of section~\ref{sec:cpu-bitonic} for purely
structural reasons. Specifically, the schedule requires comparisons between
elements arbitrarily far apart, which presupposes data exchange between tiles
and multiple passes over the input. The topology of
section~\ref{sec:npu-objectfifo} lacks these mechanisms, since the tiles work
independently and every element passes through the system exactly once.

The problem is therefore reframed. The array takes on a fixed, local task. It
independently sorts successive sequences of sixteen elements, and the host
takes on the selection, merging these sorted sequences into a heap of size k.

Because each sequence of 16 elements comes back sorted, the host can stop
examining it as soon as it encounters an element that does not exceed the root
of the heap. Because of the sorting, it is guaranteed that all the following
elements of the same sequence will be equally or more unsuitable. The sorting
on the array is not an end in itself, but a mechanism for early rejection.

\subsection{Compute tile kernel}
\label{sec:npu-bitonic-kernel}

Although an official reference implementation of bitonic sort is provided for
the AI Engine~\cite{amd2024bitonicaie}, that example is limited to a full sort
inside a single tile.

The size sixteen is dictated directly by the hardware. It corresponds exactly
to the number of 32-bit integers that fit in a vector register of the
architecture. Sixteen elements with a bitonic network need ten compare-exchange
steps, each entirely within the register.

Each step follows the same motif as in section~\ref{sec:cpu-simd}. A shuffle
brings each element next to its partner, the minimum and maximum are computed,
and a mask selects which one each position keeps. The entire network runs
without any access to the tile's memory. The data are loaded once, undergo ten
transformations in registers and are stored once.

Each invocation processes a chunk of 1024 elements, sixty-four independent
sequences. There is no dependency between them, which lets the compiler
pipeline them and hide the latencies of the individual instructions.

\subsection{Scaling to multiple tiles}
\label{sec:npu-bitonic-tiles}

The sequences are independent, so scaling to more tiles is trivial. Each one
takes on a different chunk of the batch, without synchronisation or data
exchange. Only the transfer pattern in the device configuration changes.

The implementation was extended to use two compute tiles per column instead of
one, eight in total. The extension yielded a noticeable improvement, confirming
that up to that point the implementation had been limited by the computation on
the array. More importantly, it moved the limiting factor elsewhere. With eight
tiles the array stopped being the bottleneck and the time is now spent almost
entirely on the host. Scaling to more tiles would no longer change anything.

\section{Map-reduce with local heaps}
\label{sec:npu-mapreduce}

The second algorithm follows the same work-distribution principle, with an even
more limited role for the array. Four compute tiles are used, one per column,
and the kernel does not sort. For each input chunk it computes one summary, the
best value it contains.

The host keeps the heap of size k and uses the summaries as a filter. If the
best value of an entire chunk does not exceed the root, the chunk is rejected
as a whole, without any of its elements being examined. Only the chunks that
pass the filter are examined element by element.

The filter presupposes a realistic threshold before the first chunk. On the
processor and the graphics unit this comes about automatically, since the heap
is bulk-initialised from the first k elements of the input. In the case of the
array, the host samples in advance a portion equal in size to the larger of k
and two percent of n, and inserts it directly into the heap before the first
job is dispatched, so that the filter works effectively from the start.

The array produces the information that lets the host perform the selection
cheaply, which suits its nature as fixed, local and fully predictable for
operations on a data stream.

\section{Memory management and data traffic}
\label{sec:npu-memory}

The unit has no memory of its own, and the data do not cross a bus to a
separate device, as with the graphics unit. They already reside in the same
physical memory as the host's, and what is called a transfer is in reality the
synchronisation of a shared buffer.

As far as transfer cost is concerned this is an advantage; there is no
bandwidth gap as in section~\ref{sec:gpu-memory}. There is, however, a reverse
side. Because the memory is shared, every byte the host prepares for the array
consumes the same bandwidth it would use if it performed the computation
itself.

\subsection{Pipelining and the role of the host}
\label{sec:npu-pipeline}

Less than one tenth of the time is spent waiting for the array. The remaining
ninety-two percent is work the host itself does, as the measurement of the
individual stages shows, perhaps the most illuminating result of the chapter.

So that the array does not sit idle between successive batches, execution is
organised as a three-stage pipeline, with two sets of buffers that alternate.
While the array processes one batch, the host prepares the next and merges the
results of the previous one (figure~\ref{fig:npu-pipeline}). For an input of
sixteen million integers (sixteen batches), averaged over fifteen repetitions,
the time is distributed as in table~\ref{tab:npu-phases}.

offload procedure, most of which executes on the processor.

\subsection{Data encoding and types}
\label{sec:npu-encoding}

The array's kernel operates exclusively on 32-bit integers. It does not need to
know what the values it compares represent. Every data type of this work is
therefore mapped to an integer key that preserves the relative order of the
values, following the platform's type-conversion rules~\cite{amd2024ug1079}.

The mapping differs by type. Signed integers are used as is; for unsigned ones
the most significant bit is flipped. In single precision either the sign or all
the remaining bits are flipped, depending on the sign, so that the binary
comparison coincides with the arithmetic one. Half precision is first widened
to single (an exact conversion) and follows the path above.

The encoding runs on the host and forms part of the preparation stage of
table~\ref{tab:npu-phases}. Handling the data type burdens only the processor
computationally. In fact, the initial, scalar implementation of the
half-precision encoding proved so expensive that it noticeably delayed the
whole stage. For this reason, it was replaced by a vectorised path that
converts eight values per instruction.

\subsection{Final correction on the host}
\label{sec:npu-refinement}

Double precision does not fit in a 32-bit key. The encoding keeps the 32 most
significant bits of the full 64-bit key, so two different values can end up
with the same key. The array returns something weaker than the exact result: a
threshold.

An additional stage on the host restores correctness. From the keys the array
returned, the worst one is taken, which defines the threshold. The host
traverses the entire input again, collects the elements whose key falls within
the threshold and performs exact selection among them.

The cost is one extra pass over the input, which exceptionally burdens double
precision. The benefit is that the result is exact and passes the same
correctness check as all other data types, without relaxing the criterion. An
approximate result for a single type would make the comparison across types
unequal.

\section{Reference implementation}
\label{sec:npu-reference}

The baseline is the same standard-library function as for the processor, run
entirely on the host. The reasons for this choice were discussed in
section~\ref{sec:meth-baseline-libraries}. It is only worth recalling the
essential point: there is no top-k implementation for the array itself.

\section{Limiting factors}
\label{sec:npu-bottlenecks}

The limiting factor is already visible in table~\ref{tab:npu-phases} and it is
the host. But why is the host's work so expensive?

The preparation stage (three-fifths of the time) comprises a full read pass
over the input, the conversion of each element into an integer key and a write
of equal volume to the shared buffer. In total this gives data traffic at least
twice the input size, over the same memory and at the same bandwidth the
processor would use. The merge adds yet another read pass over the results.

Even if the array completed its own work instantaneously, the total time would
drop by less than one tenth, since the time is not spent there. The speed-up
therefore cannot come from the device.

The comparison with the processor sharpens the argument. The host that feeds
the unit is the same processor that solves the entire problem on its own. Here
it is asked for almost the same amount of data traffic, merely to prepare the
data for someone else. The cost of preparation is comparable to the cost of the
solution itself, which is why the offload does not pay off.

This conclusion, however, concerns this particular problem. Top-k selection has
minimal operational intensity, with one comparison per element and almost no
reuse. A dataflow array performs well when every element that enters it
undergoes many operations, so that the feeding cost is amortised. Here the
opposite happens, and this mismatch between the problem and the architecture
explains the result better than any implementation detail.
