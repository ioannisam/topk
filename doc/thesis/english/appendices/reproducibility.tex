\chapter{Reproducing the Measurements}
\label{app:reproducibility}

This appendix describes the steps required to reproduce the thesis's
measurements, from installing the tools to generating the plots. The commands
are given for the system described in Section~\ref{sec:meth-machine} and are
executed from the root of the repository.

\section{Software Requirements}
\label{sec:repro-requirements}

All three implementations require a C++ compiler that supports the C++20
standard, together with CMake version 3.18 or newer. Vector instructions are
not a compilation requirement: the choice between AVX-512, AVX2 and scalar
execution is made at run time, based on the capabilities reported by the
processor. The thesis's measurements were obtained on a processor with
AVX-512, so on a machine without it the CPU follows a different code path and
its results are not directly comparable. Beyond these, each architecture has
its own requirements.

The GPU requires the CUDA toolkit with the nvcc compiler and the CUB library,
which is distributed together with it. Power measurements additionally
require the NVML library, which ships with the driver.

The NPU requires the XRT runtime stack together with the XDNA device plugin,
and, for compiling the kernels, MLIR-AIE within a Python environment. This
environment must reside at the root of the repository under the name
npu\_venv, since both kernel compilation and the automated execution of the
measurements look for it there. The user must belong to the groups that have
access to the device, and the locked-memory limit must be sufficient;
otherwise the device is not visible to the runtime stack. The XILINX\_XRT
variable must point to the installation location of XRT.

Energy measurement reads the RAPL counters through /sys/class/powercap,
which requires elevated privileges. In a single run, without these the
measurement is explicitly reported as unavailable rather than reporting zero
values, as described in Section~\ref{sec:meth-energy}; the corresponding
sweep, by contrast, does not even start and terminates with an error, so that
no empty dataset is produced. Finally, the analysis infrastructure requires
Python with the libraries declared in the repository; the corresponding
environment is created automatically the first time it is run.

\section{Compilation}
\label{sec:repro-build}

Compiling all implementations is done with a single command:

\begin{verbatim}
make build-all
\end{verbatim}

Each architecture can also be compiled separately, using the build-cpu,
build-gpu and build-npu targets, which is useful on a system that does not
have all three units. The resulting executables are placed in the build
directory, two per architecture: one for the top-k measurements and one for
the roofline measurements of Section~\ref{sec:meth-roofline}.

Compilation for the NPU additionally produces the hardware configuration
files. Because their absence leads to the corresponding measurements being
silently skipped, their presence is checked explicitly:

\begin{verbatim}
make verify-artifacts
\end{verbatim}

The check covers the two configuration files and the three top-k measurement
executables, so it presupposes a full compilation of all three
implementations; after compiling only a single architecture it fails by
default.

\section{Running the Experiments}
\label{sec:repro-run}

The recommended way to reproduce the results is not to run the individual
steps, but a single command that executes the entire procedure:

\begin{verbatim}
make benchmark GPU_W=50
\end{verbatim}

The reason this is the preferred route is not convenience, but consistency.
The order of the steps matters: if the system conditions are pinned after the
measurements have started, or if a sweep is run with executables from an
earlier compilation, the results are not comparable to one another. The
command enforces the correct order and leaves no room for a step to be
skipped.

The sequence that runs consists of six stages. First, the previous results
and old executables are deleted, so that nothing survives from an earlier
run. Next, all three implementations are compiled and the presence of the
resulting files is checked, using the check from Section~\ref{sec:repro-build}.
In the third stage, the system conditions are pinned and read access to the
energy counters is granted. In the fourth, the four sweeps are run in
sequence; in the fifth, the plots for each of them are generated; and in the
sixth, the original system conditions are restored.

Two preconditions are checked before anything else: the availability of sudo
and the existence of the npu\_venv environment from
Section~\ref{sec:repro-requirements}. If either is missing, the command
terminates immediately, without altering the system or the existing results.

Three properties of the command are worth noting. Administrator privileges
are requested only once, at the beginning, and remain active for the entire
duration, so the run requires no further intervention afterwards. The
conditions are restored in every case, even if the run is interrupted by the
user or terminates with an error, so that the system is not left pinned.
Finally, the failure of one sweep does not cancel the rest: it is logged as a
warning and the procedure continues, so that a partial run nonetheless
produces whatever data it was possible to measure.

The GPU\_W argument sets the power limit of the GPU, which, according to
Section~\ref{sec:meth-conditions}, must remain constant throughout the
sweep. It should also be stressed that the command deletes the existing
results as its first step, so any previous measurements that need to be kept
must first be copied elsewhere.

\subsection{Running Individual Steps}
\label{sec:repro-steps}

For a partial or repeated run, each stage is also available separately. The
system conditions are controlled with:

\begin{verbatim}
make pin ARGS=50      # governor, boost off, GPU cap 50 W
make pin-show         # report the current state
make unpin            # restore governor, boost, GPU cap
\end{verbatim}

The measurements are divided into four independent sweeps, each of which
writes its raw results to a separate file:

\begin{verbatim}
make measure-cases      # timing over the parameter space
make measure-energy     # energy, requires RAPL access
make measure-dists      # input-distribution sensitivity
make measure-roofline   # bandwidth, compare-exchange roofs
\end{verbatim}

Each target accepts additional arguments through the ARGS variable, which are
forwarded to the sweep driver and allow the parameter space to be restricted
to a subset of it. This is useful for quickly checking the installation,
where a full sweep would be excessively time-consuming. When the stages are
run separately, responsibility for the correct order and for the stability of
the conditions between sweeps rests with the user.

\subsection{Execution Parameters}
\label{sec:repro-cli}

Table~\ref{tab:cli} gives the full set of parameters accepted by each
executable, their permitted values, their defaults, and the values with
which the thesis's sweeps were run.

The defaults are those of the executable and in several cases do not match
the values used in the sweeps. The value range extends up to $10^9$ instead
of the default, and the reason is substantive: with a range of only a few
thousand values and an input of millions of elements, value repetitions
would be so dense that the problem would turn into a choice among ties,
which would artificially favour algorithms that reject quickly.

This range applies to four of the five types. For half, the executable
clamps the bounds to $\pm 65504$, the largest finite value it can represent,
so sampling actually takes place over $[0, 65504]$. For this type, ties are
not avoided, both because of the narrower range and because above $2048$
half does not represent every integer. This is an inherent property of the
type rather than a methodological choice, but it must be taken into account
when interpreting its results.

The seed is not fixed, but is generated deterministically from the q and k
of each case, so that two different cases never receive the same input
while each case remains reproducible.

The values in the fourth column refer to the main sweep. The two special
sweeps restrict certain parameters: the distribution sweep examines q from
20 to 24, only the float and half types, and the k extremes 8 and 131072,
with two seeds per case; the energy sweep examines q from 16 to 24 with
three repetitions and without correctness checking, so that the check is
not counted toward the consumption.

\section{Generating the Plots}
\label{sec:repro-plots}

The analysis infrastructure reads the raw results of the sweeps, converts
them into tables in CSV format, and generates the plots:

\begin{verbatim}
make plot ARGS="--plot all"
\end{verbatim}

The --plot argument selects which plots will be produced, while --input
specifies which sweep will be read; the default is the timing sweep. The
energy, distribution and roofline plots read their own files, so it is
usually preferable to use the combined targets, which run the measurement
and the corresponding plot generation together:

\begin{verbatim}
make benchmark-cases
make benchmark-energy
make benchmark-dists
make benchmark-roofline
\end{verbatim}

The resulting files are organised by data type and by measurement category,
together with the tables from which they were derived. Plots that concern
the machine itself, such as the bandwidth scale of
Section~\ref{sec:meth-roofline}, are placed in a separate directory, since
they do not depend on the data type.

Two options affect the interpretation of the plots and are worth mentioning.
--energy-metric selects between gross energy, net energy, or both together,
which is also the executable's default; the thesis's sweeps explicitly
request the net figure, for the reasons given in
Section~\ref{sec:meth-energy}. --error-bars selects the kind of dispersion
band drawn around the values, among standard deviation, deciles, or no band
at all, with standard deviation as the default. A band is drawn only where
there are at least two samples per point, namely in the distribution sweep,
which uses two seeds per case, and in the energy sweep, which repeats each
case three times. In the automated run, the bands are disabled for all four
sweeps, so the plots it produces do not include them.
